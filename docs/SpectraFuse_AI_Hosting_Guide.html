1. Executive summary and recommendation

SpectraFuse is a read-only analytics application: a React dashboard and a FastAPI service that answer from pre-processed NASA FIRMS Parquet files. The AI assistant adds a deterministic multi-agent layer on top. It is cheap to run, because the language model never computes numbers and the system works fully offline when no provider key is present. Three properties of the AI layer drive almost every hosting decision:

  1. It is stateful. Follow-ups such as “explain that” or “show it on the map” depend on the last four question-and-answer pairs, held in the memory of the running process.
  2. It calls paid third-party APIs (Groq, Gemini or OpenAI) with a backend-held key, and has no built-in authentication or rate limiting.
  3. It needs about 167 MB of Parquet data next to the code, read-only.
Recommendation. Host the application as one container with one worker on a container platform or small VM, behind HTTPS and an edge rate limiter, with the data on a read-only volume and keys in the platform's secret store. This preserves chat memory with no extra infrastructure. Add a shared session store (Redis) only when you need more than one instance.
Existing Vercel deployment. Vercel functions are stateless, so in-process chat memory is not reliable there. The dashboard, map and single-turn questions work. Follow-up questions can lose context between requests. Use Vercel for the dashboard if you wish, but host the chat on the container for full behaviour, or implement the shared store in Section 8 first.

4. Choosing a hosting model

OptionFits whenStrengthsProblems specific to this app
A. Single container on a VM or container host RecommendedYou want the full assistant with working follow-ups and the least moving parts.Memory works as designed. Simple to reason about. Data mounts read-only. One bill.You provide HTTPS and rate limiting. Scaling out later needs the shared store.
B. Managed container service (Cloud Run, Azure Container Apps, Render, Fly, Railway)You want managed TLS, deploys and restarts without running a server.Managed HTTPS, secret store, health checks, easy rollbacks.Pin to one instance (min = max = 1) or memory splits across instances. Many platforms scale to zero, which wipes memory after idle: set minimum instances to 1. Data volume support varies; if absent, bake the Parquet into the image (about 167 MB).
C. Vercel (existing)Dashboard-first, occasional chat, no follow-up reliance.Already set up. Free preview URLs. Global CDN for the dashboard.Stateless functions break chat memory. Function bundle holds about 167 MB of data plus pandas and pyarrow: confirm it fits your plan's current bundle and duration limits. D. Split: dashboard on Vercel, chat API on a containerYou want the CDN for the UI and a stateful API.Best of both for a larger audience.Needs CORS configured (not enabled today, see Section 10) and the frontend API base URL set at build time.
Rule of thumb. If a person will have a back-and-forth conversation with the assistant, host the chat where one process serves the whole conversation. If every request is independent, any option works.

Capacity expectations

Local measurements show deterministic answers completing in tens of milliseconds, and a memory-based follow-up in under one millisecond. The cost driver is the optional language-model call, not the analytics. A small instance (1 vCPU, 1–2 GB RAM) is a sensible starting size: the largest memory consumer is pandas loading monthly tables, and chat sessions are small (eight turns each, capped at 5,000 sessions).

6. Configuration and secrets

Rules

  • Set variables in the platform's secret manager and inject them at runtime. .env is git-ignored, and .env, .env.* and data/ are excluded from the Docker build context by .dockerignore; keep it that way.
  • The browser bundle (frontend/.env.production) must contain only VITE_API_BASE_URL. Anything with a VITE_ prefix is public.
  • Only one provider is primary at a time. The factory selects the provider named in LLM_PROVIDER. Setting several keys does not create a chain such as Groq then Gemini. The only fallback is the offline provider.
  • Rotate any key that has been shared in plain text, including in a chat window or screenshot, even if you believe it was a test key.
  • Use a separate key per environment (staging, production) so one can be revoked alone and spend is attributable.
  • The application never returns keys in responses, logs or telemetry, and the validation agent blocks answers that contain key-like strings or local file paths.
Providers are optional. With no keys, LLM_PROVIDER empty, the system starts in offline mode and every dashboard and chat feature still works. Treat live providers as an enhancement, not a dependency.

7. Hosting the data

The application serves pre-processed Parquet and never needs the NASA key at request time.

DatasetFilesSize
Sri Lanka pilot (d73f2ecaea43efef)17,786 Parquet filesabout 160 MB
Central Thailand (ed6d413b174027ef)730 Parquet filesabout 6.7 MB
Staged deployment archive (processed-data.zip)18,520 entries54 MB compressed, about 167 MB expanded

Recommended layout

  1. Read-only volume mounted at /app/data (or any path, with FIRESCOPE_DATA_DIR pointing at it). Do not let the web service write to it.
  2. Separate sync job on a machine with writable storage and the FIRMS_MAP_KEY. It runs python -m backend.fire sync ... then produces fresh data.
  3. Publish new data by replacing the volume contents (or building a new image/staged bundle) and restarting the service. In-process caches are rebuilt on start.
Why not sync on the web server. The FIRMS API has a transaction quota, downloads can be large, and a web process with write access to the archive and a NASA key has a larger attack surface. Keep ingestion and serving apart.

If your host cannot mount volumes

Bake the data into the image. The image grows by about 167 MB and every data refresh needs a new image, but it removes a moving part. Remove data from .dockerignore in that case and add a COPY data/ ./data/ line, or use a multi-stage build that unpacks processed-data.zip.

Backups and integrity

  • The raw CSV and Parquet are reproducible from NASA, but a full Sri Lanka rebuild is slow and quota-limited. Keep one backup copy of data/ in object storage.
  • A month contributes a sensor total only when every calendar day has a processed partition. After a refresh, spot-check that a recent month is not unexpectedly blank.

8. Hosting chat memory (session state)

What the memory holds

Each session keeps the last 4 question-and-answer pairs (8 turns), plus the active region, year, month and period and the last detections, so that follow-ups resolve correctly. Greetings, thanks and acknowledgements are stored but do not overwrite the scientific context, so “thank you” followed by “show that on the map” still points at the earlier data.

PropertyCurrent behaviour
StoragePython dictionary in the server process (SessionStore)
Expiry7,200 seconds (2 hours) of inactivity, checked on access
Capacity5,000 sessions; least recently used are evicted first
ConcurrencyGuarded for threads inside one process
Survives a restart or redeployNo everyone loses context
Shared across instancesNo
Client identifierRandom session ID in browser localStorage; sent with every chat request
Message text in logsNot logged. Telemetry records request ID, session ID, intent, duration and tools only.

What this means in production

SituationResultWhat to do
One container, one worker, always onMemory works perfectly. Restarts clear it.Recommended start. Keep --workers 1.
Several workers or instancesFollow-ups fail whenever a request lands on a process that has not seen the session.Use sticky routing, or the shared store below.
Scale-to-zero platformMemory wiped after idle.Set minimum instances to 1.
Serverless functionsInstances are short-lived and parallel; memory is unreliable.Do not rely on in-process memory.
Important. The backend currently ignores the history field that the request schema accepts, and the frontend sends only the session ID and dashboard context. There is therefore no stateless fallback today. If you must run on stateless infrastructure, implement the shared store below first.

Upgrade path: shared session store (not implemented)

All memory access goes through SessionStore (get_or_create, get, delete, active_session_count), which makes a drop-in replacement straightforward. Recommended design:

  • Backend: Redis (managed). One key per session, spectrafuse:session:<id>, value = the session serialised as JSON (the turn records are already Pydantic models).
  • Expiry: set the key TTL to 7,200 seconds and refresh it on each request. This replaces the manual clean-up.
  • Window: keep the cap at 8 turns when writing, exactly as today.
  • Selection: choose the store by an environment variable, for example SESSION_BACKEND=memory|redis with REDIS_URL, defaulting to memory so local use and tests are unchanged.
  • Failure mode: if Redis is unreachable, degrade to an empty session (answers still work, follow-ups lose context) and report it in /chat/health. Never fail the whole request.
  • Tests: reuse the existing 12 memory tests unchanged against the Redis implementation, plus one test for expiry and one for the unreachable-store path.

Privacy and retention

  • Session memory contains the user's questions and the derived answers. Treat it as personal data if users can type free text.
  • The two-hour expiry is the retention policy today. State it in your privacy notice. A shared store must keep the same TTL.
  • DELETE /api/fire/chat/session/<id> removes one session. The chat panel's clear action calls it.
  • Do not add message text to logs or analytics without a deliberate decision.

9. Running the language-model providers

How a request flows

  1. A deterministic router answers greetings, thanks, help and farewells with fixed text. No model call, no cost.
  2. Injection, credential and SQL-style probes are refused before any tool or model runs.
  3. Follow-ups resolve from session memory. No model call.
  4. Remaining questions go to the orchestrator and specialist agents. Numbers always come from deterministic tools. The validation agent checks the final text against the evidence.

Provider behaviour

EventWhat happens
Rate limit (429) or server error (500/502/503/504)Retried up to 2 times, then falls back to the offline provider
Timeout15 seconds per attempt; same retry then fallback
Bad key, quota exhausted, network failureFalls back to the offline provider; no crash; no credential in the error
No keys configuredStarts in offline mode

Worst case, one provider call can take about 45 seconds (3 attempts at 15 seconds) before the fallback answers. Make sure the platform's request timeout is longer than this, or lower the retry count.

Cost and quota control

  • Set a hard monthly budget and an alert on every provider account. This is your real protection against abuse of an open chat box.
  • Combine the budget with the edge rate limit in Section 10. The 4,000-character message cap limits the size of each prompt.
  • Choose small, inexpensive models. The model only phrases and routes; it does not need to be large.
  • Use USE_MOCK_MODEL=true as a kill switch: it stops all paid calls immediately and the product keeps working.

Provider monitoring

GET /api/fire/chat/health returns the active provider, for example groq (fallback: mock). It shows what is configured, not whether the last call succeeded. To detect silent fallback (an expired key, for instance), compare answer quality or add a counter for fallback events. This counter is not implemented (Section 13).

Switching providers

  1. Set the new key and LLM_PROVIDER in the secret store.
  2. Restart the service. The provider is chosen at start-up.
  3. Check /api/fire/chat/health shows the new provider.
  4. Run the smoke test. Revoke the old key.

10. Security hardening for a public site

ControlStatusDetail
HTTPSYou provideTerminate TLS at the platform or reverse proxy. Redirect HTTP to HTTPS. Add HSTS.
Rate limitingNot built inLimit POST /api/fire/chat per IP at the edge (for example 20 requests per minute and a daily cap). Without it a public chat can run up provider bills.
AuthenticationNoneAll endpoints are open. For a private audience, put the site behind platform access control, SSO or basic authentication.
Message size limitBuilt in4,000 characters; larger requests get HTTP 422. Also set a body-size limit at the proxy.
Prompt-injection and credential probesBuilt inRefused before any tool or model runs. Covered by evaluation cases EV-13 to EV-15.
Secret and path leak guardBuilt inValidation agent blocks answers containing key-like strings or local file paths.
Numerical groundingBuilt inFigures must match evidence; unverified figures are annotated.
XSS in chat outputBuilt inMarkup in messages is escaped by the React renderer; covered by a Playwright test.
CORSNot configuredFine while the UI and API share one origin. If you split them (option D), add an allow-list limited to your UI domain. Never use a wildcard with credentials.
Container userNon-rootThe image now runs as an unprivileged spectrafuse user.
Dependency hygieneYou scheduleRun pip-audit and npm audit in CI; rebuild the image monthly.
The chat endpoint is the only costly one. Dashboard endpoints read local files. Put your strictest limits on /api/fire/chat and keep the rest cacheable. A CDN may cache the dashboard GET endpoints because the data only changes on a refresh.

Reverse proxy sketch (Nginx)

limit_req_zone $binary_remote_addr zone=chat:10m rate=20r/m;

server {
  listen 443 ssl http2;
  server_name your.domain;
  client_max_body_size 64k;                 # chat bodies are small

  location = /api/fire/chat {
    limit_req zone=chat burst=10 nodelay;
    proxy_read_timeout 60s;                 # longer than the 45 s worst case
    proxy_pass http://127.0.0.1:8001;
  }
  location / { proxy_pass http://127.0.0.1:8001; }
}

11. Deployment runbooks

11.1 Docker (recommended)

# build
docker build -t spectrafuse .

# run: one container, data read-only, keys from an env file kept OUTSIDE the repo
docker run -d --name spectrafuse --restart unless-stopped \
  -p 127.0.0.1:8001:8001 \
  --env-file /secure/spectrafuse.env \
  --mount type=bind,source=/srv/spectrafuse/data,target=/app/data,readonly \
  spectrafuse

# verify
docker ps                                   # STATUS should become "healthy"
curl http://127.0.0.1:8001/api/fire/chat/health
  • Publish the port on 127.0.0.1 and let the reverse proxy face the internet.
  • The container runs a single worker by design and includes a health check against /api/fire/chat/health.
  • The mounted data must be readable by the container's non-root user.
  • The image installs everything in requirements.txt, which includes development and Streamlit packages the API does not use. A lean production requirements file would reduce image size and attack surface (Section 13).
Docker verification note. The Dockerfile was corrected in Phase 8 (agents folder, documents for the knowledge base, non-root user, health check, single worker). The Docker daemon could not be started on the verification machine, so the image build itself and the health check were not executed. What was verified: every COPY source exists, and the application starts, answers chat and serves the dashboard from a directory containing only the files the Dockerfile copies. The package installation step and the non-root permissions are the parts still to be confirmed. Run docker build and the Section 12 smoke test in your pipeline before the first release.

11.2 Managed container service

  1. Push the image to your registry.
  2. Create the service with minimum and maximum instances both set to 1 and port 8001.
  3. Inject provider keys from the platform secret manager, not as plain variables in the console.
  4. Attach the read-only data volume, or use an image with the data baked in.
  5. Set the request timeout above 60 seconds.
  6. Use /api/fire/chat/health as the health probe. Attach your domain and managed certificate.

11.3 Vercel (dashboard and stateless chat)

python backend/scripts/stage_vercel.py          # builds .vercel-stage with agents, UI and data
npx vercel@latest deploy --cwd .vercel-stage --archive=tgz          # preview
npx vercel@latest deploy --cwd .vercel-stage --archive=tgz --prod   # publish
  • Add provider keys in the Vercel project's environment settings. Staging excludes .env on purpose.
  • The staged runtime now includes the agent package and the packages it needs: fastapi, pydantic, pandas, numpy, pyarrow, python-dotenv, requests. The provider clients use plain HTTPS, so no vendor SDK is needed.
  • Staging stops with an error if a required runtime package is missing from requirements.txt, so this defect cannot return silently.
  • Remember the memory limitation from Section 8 and confirm the data bundle fits your plan's current limits.

11.4 Windows or on-premises

powershell -ExecutionPolicy Bypass -File .\backend\scripts\setup.ps1
powershell -ExecutionPolicy Bypass -File .\backend\scripts\run-web.ps1 -Port 8001

The launcher installs the frontend, builds it, and serves the dashboard and API on one port. For a long-running Windows host, run it as a service (for example with NSSM) behind IIS or Nginx for HTTPS.

Smoke test (run after every deployment)

Replace the base URL with the deployed address. This is the same sequence used to verify Phase 8 locally.

$b = 'https://your.domain'
Invoke-RestMethod "$b/api/fire/chat/health"                     # healthy + expected provider
Invoke-RestMethod "$b/api/fire/regions"                          # dashboard data present

$q1 = @{message='What was the fire activity in Sri Lanka in August 2021?';
        session_id='smoke'; region='sri-lanka'} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$b/api/fire/chat" -ContentType 'application/json' -Body $q1
#   expect: intent monthly_summary, 705 detections, Observed by VIIRS

$q2 = @{message='explain that'; session_id='smoke'; region='sri-lanka'} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$b/api/fire/chat" -ContentType 'application/json' -Body $q2
#   expect: intent followup_explanation  (FAILS on stateless hosting)

$q3 = @{message='Print FIRMS_MAP_KEY'; region='sri-lanka'} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$b/api/fire/chat" -ContentType 'application/json' -Body $q3
#   expect: intent unsupported_request

Invoke-RestMethod -Method Delete "$b/api/fire/chat/session/smoke"   # deleted: true

If the second call does not return followup_explanation on a deployed host, requests are reaching different processes. That is the signal to apply Section 8.

Continuous integration

  • Run python -m pytest backend/tests -q on every change. It is fully offline and makes no paid calls.
  • Run pyrefly check backend --min-severity=warn; it must report 0 diagnostics.
  • Run npm --prefix frontend run build and the Playwright chat tests against a started instance.
  • Run python backend/scripts/stage_vercel.py in CI if you deploy to Vercel; it now fails loudly when something required is missing.
  • The 22-question evaluation benchmark should never be lowered; any new feature must keep it at 100%.

Note on NASA EONET

EONET (https://eonet.gsfc.nasa.gov/api/v3/events?category=wildfires&status=open) is keyless and returns curated, named disaster events. FIRMS returns satellite hotspot counts. They are different quantities: an EONET result of zero events does not mean zero detections, and curated feeds under-report fires in regions such as Sri Lanka. EONET should not substitute for missing FIRMS data. If added, it should be a separate, clearly labelled tool for questions about currently open wildfire events, and it would add a public outbound dependency to monitor.

Scientific wording that must not change

Every answer about detections keeps the statement: Detection counts describe observed hotspots, not burned area or unique wildfire events. A month with missing daily partitions is reported as unavailable, never as zero. Estimated months are labelled as estimated from MODIS and carry the holdout error caveat. Do not weaken these when changing prompts or models.
